# LASTONE

災害で手元の薬を失った人に、別の地方に預けた本人の薬を届ける Web アプリ（デモ）。
本人の薬の7日分を自宅と別の地方の「薬バンク」で預かっておき、災害が起きたら、
道路の寸断とドローンの便の数から、間に合う人数が最大になる順番で届ける。

画面の人・地区・薬局・道路・数字はすべて架空のデモデータ。薬バンクやドローン会社との協定はまだない。

## 動かし方

公開版（GitHub Pages）：https://vpgkotaro-jpg.github.io/lastone/ （サーバーへの送信はなく、記録は端末にためる）

```
node server.js          # http://localhost:8080/ を開く（Node 18 以降。外部ライブラリなし）
```

`index.html` をブラウザで直接開いても動く（その場合はサーバーへの送信とオフライン動作がない）。
カメラでの読み取りは https か localhost で開いたときだけ使える。

URL の末尾で、見せたい場面を直接開ける。

| URL | 場面 |
|---|---|
| `#lost` | 患者アプリ：家が壊れて手元の薬を失った |
| `#triage` | 係員の端末：地図・届ける順番 |
| `#cap` | ドローン1拠点1日1便のときの比べ方 |
| `#card` | 避難所カードを読み込んだあと |

## テスト

```
node --test test/*.test.js     # 33件が通る（外部ライブラリなし。3件は jsqr・pngjs がないと飛ばす）
npm install && npm test        # jsqr・pngjs を入れると36件（生成した QR を jsQR で読み戻す、スクリーンショットから読む）
node bench.js                  # 配送計画の速さと、比べる方法ごとの結果、QR 読み取りの速さ
node test/compare-jsqr.js      # 自作の読み取りと jsQR を同じ合成画像200枚で比べる（ぼかしなし・ありの2通り。npm install のあと）
```

## ファイル

| ファイル | 中身 |
|---|---|
| `lastone-core.js` | 画面に依存しないロジック。危険になる日、配送計画（1拠点：締切順の貪欲法／複数拠点：増加路による割り当て）、道路の寸断から届け方を出す処理、カードの署名の検証、読み取り記録の突き合わせ、QR 生成 |
| `qr-read.js` | QR の読み取り。位置検出パターンの検出、射影変換、形式情報、Reed–Solomon の誤り訂正（Berlekamp–Massey・Chien 探索・Forney） |
| `demo-data.js` | 架空の24人・6地区・道路・ドローン拠点・薬局と、カードの署名 |
| `app.js` | 画面（患者アプリと係員の端末） |
| `server.js` | 静的ファイルと、読み取り記録を受け取る API（`POST /api/scans`）。カードの署名をサーバーでも確かめ、期限はサーバーの日付で比べ、`data/scans.json` に突き合わせて保存する。一覧（`GET /api/scans`）は係員の鍵（環境変数 `LASTONE_STAFF_KEY`、ヘッダー `x-lastone-staff`）がないと返さない |
| `tools/issue-cards.mjs` | 発行側の道具。薬バンクの秘密鍵で、名簿の一人ずつに署名する。秘密鍵はリポジトリに入れない |
| `sw.js` | 一度開けば、通信がなくても画面とロジックが動く（https か localhost のとき） |
| `test/` | Node のテスト |

## 決めたこと

- 避難所には通信がない前提。カードは文字と署名だけの QR にして、係員の端末は圏外でも署名と期限を確かめられるようにした。手元の日数といる場所は本人の申告なので署名の外にあり、係員が確かめて記録に印をつける。
- ドローンの便が足りないとき、締切順に並べるだけだと、どうやっても間に合わない人に枠を使ってしまい、登録順より悪くなることがある（`#card` の場面＝Aさんが手元0日、1拠点1日1便：車で行けない11人のうち届く前に切れる人が、登録順6人、締切順だけ7人、この割り当て3人。`#cap` の場面＝Aさんが手元2日では5人・7人・2人）。デモの町では、差のほとんどは「間に合わない人を飛ばす」ことで出ている。
- 拠点が複数あり、地区ごとに飛べる拠点が違うと、締切順に近い拠点の枠を埋めて飛ばすだけでは最適にならない（片方からしか届かない人の拠点を、両方から届く人が先に使う）。二部マッチングの増加路で入れる。全探索との比較テスト3,000問で人数が一致。拠点が横に並び人が町の中心に多い架空の町（1,000人・拠点5）では、届く前に切れる人が「飛ばす」方法の117人に対して100人（`node bench.js`）。デモの24人の町では同じ人数になる。
- 読み取り記録は、端末どうし・端末とサーバーで何度合わせても、どちらから合わせても同じ結果になるようにした（テストで確かめている）。

## まだできていないこと

- ログインと、医療情報の暗号化（いまはカードに薬の名前が平文で載る）
- 実際の道路の通行情報とのつなぎ込み（いまは地図の道路を手で開け閉めする）
- 実機での読み取りは iPhone 14 の1台だけで測った。印刷したカードを公開版の `#triage` の「カメラで読む」で読み、明るい所の正面・斜め約30度・少し暗い所を各5回の15回はすべて読めた。紙を曲げた5回は2回だけ（合計20回中17回）。Android ではまだ測っていない
- QR 読み取りは右下の位置合わせパターンだけを使う。大きく曲がった紙や、型番の大きい QR の斜め撮りは読めないことがある。実機でも、曲げた紙は5回中2回しか読めなかった。次は、型番の大きい QR にある位置合わせパターンを全部使い、格子を区画ごとに合わせて、曲がりに強くする
- ログインがない。読み取り記録の受け取りは署名で確かめるだけで、送ってきた端末が係員のものかは確かめていない。カードを持っている人なら、同じ記録 ID で中身（手元の日数・場所・確認）を上書きできてしまう
- 患者アプリの「手元の薬を失った」は端末に記録するだけで、まだどこにも送らない
- QR 読み取りはぼかしに弱い（ぼかしを足した合成画像200枚で自作68枚、jsQR 85枚。`node test/compare-jsqr.js`）
- 配送計画は「1便で1人分を運ぶ」前提。実際には1便で同じ避難所の何人分かを運べるので、避難所を単位にした割り当てに置き直す必要がある
- 最初に預ける7日分は、手元の残薬を宅配で預けるか、残薬がない人は卸の在庫を引き当てて始める想定。費用を誰が持つかは決まっていない
